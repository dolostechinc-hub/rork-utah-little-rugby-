## Learned User Preferences

- Apply Supabase migrations manually via the Supabase Studio SQL Editor; do not rely on the Supabase CLI.
- Test the Expo app on a phone using Expo Go in tunnel mode (not LAN, not a bare workflow).
- For pickers like clubs, use a strict canonical list with no free-text entry and no auto-create-from-typed-value, to prevent variant spellings.
- Use Bun as the package manager inside `expo/` (`bun install`); start the dev server via `node node_modules/expo/bin/cli` rather than `bunx expo`, which mis-resolves the project root.
- During roster dedupe, merge rich fields onto the kept canonical row and preserve any record that has `photo_uri`, `weight`, `is_age_verified`, `checked_in`, or `parent_phone` — never delete a duplicate that is richer than its survivor.
- Tie admin/editor authority to the Supabase auth user (email-based allowlists / RPCs), not to a device or local PIN, so the app cannot become orphaned when a device-bound PIN expires or a phone is replaced.
- When standing up a new season's org, copy ALL rich roster state forward in the same migration (`checked_in`, `division`, `age_group`, `photo_uri`, `weight`, `is_age_verified`, `restriction_status`) — a player with both a `weight` and a `photo_uri` should be marked `checked_in=true` automatically; a "fresh" org that re-shows already-completed kids as pending is a bug, not the desired blank slate.
- Roll seasons by creating a brand-new org and flipping prior orgs to `organizations.is_active=false` rather than re-using or mutating the old org; this keeps history queryable, avoids cross-org ID collisions, and lets the org picker hide retired seasons without deleting roster data.

## Learned Workspace Facts

- The Expo app lives in `expo/`; the workspace root is a Rork workspace (has `rork.json`), so `expo/package.json` — not the root — is the project's package.json.
- Start the Expo dev server with `cd expo && PATH="/opt/homebrew/bin:$PATH" node node_modules/expo/bin/cli start --tunnel --clear`; the explicit Watchman PATH (Watchman is at `/opt/homebrew/bin/watchman`) prevents Metro `EMFILE` errors.
- Supabase migrations live in `expo/supabase/migrations/NNN_name.sql` and are applied manually in Supabase Studio's SQL Editor. The editor uses transaction-pooled (pgbouncer) connections so `CREATE TEMP TABLE … ON COMMIT DROP` does not survive across statements (use inline `VALUES` CTEs), `EXPLAIN` only accepts a single statement, and `RAISE NOTICE` output is swallowed in the results pane — emit progress as a final `SELECT`/`RETURNING` row instead of relying on notices. Long ad-hoc analyses are written as one CSV-returning query and the user pastes the CSV back into chat.
- `expo/lib/supabase.ts` has hardcoded production Supabase URL + anon-key fallbacks, so the dev app (Expo Go tunnel) reads and writes PRODUCTION Supabase data without an `.env` — treat the local dev environment as live and never run destructive ad-hoc writes from it.
- `public.roster_players` is keyed by composite PK `(org_id, id)` (migration 024); upserts must use `onConflict: 'org_id,id'` and IDs come from `randomId()` in `expo/lib/ids.ts` (never `Date.now()` — collides across orgs/devices). `client_updated_at` is the client-side conflict-resolution clock; `updated_at` is rewritten by a server trigger and is not client-trustworthy. All reads MUST paginate via `.range()` chunks (PostgREST 1000-row cap) — see `fetchRoster` in `expo/lib/rosterSync.ts`; the dedupe in `mergeRemoteRoster` is local-view only and must never call `deleteRosterPlayer` or push "canonical" winners back to Supabase.
- Canonical clubs live in `public.clubs` (migration 025) and are fetched through `expo/lib/clubsRepo.ts`; the offline fallback in `expo/mocks/registrationData.ts` must mirror the seed list. `roster_players` denormalizes the choice via a free-text `club` column AND a `club_id` FK (`roster_players_club_id_fkey` → `public.clubs(id)`); mass renames (e.g. adding the "Little " prefix) should edit `public.clubs.name` so the FK cascade flows to roster rows — the text `club` column will drift and should not be bulk-edited row-by-row.
- `roster_players.date_of_birth` is a TEXT column with mixed formats (`M/D/YYYY`, `MM/DD/YYYY`, long-form like "January 1, 2016") plus dirty values (`03/032014` missing slash, `08/29/2917` typo year, `15/20/2015` invalid month); strict `to_date` casts fail — use the format-tolerant parser/preview in `expo/supabase/migrations/038_*` before tightening the column type. Imported names also carry UTF-8-as-Latin1 mojibake for typographic apostrophes (`â€™`, `â€˜`); repair via `convert_from(convert_to(name, 'LATIN1'), 'UTF8')` (migration 034) before fuzzy dedupe so mojibake twins cluster with their clean counterparts.
- Hidden triggers added via the Supabase Studio UI (NOT in the migration files): `block_blank_roster_inserts_trigger` rejects new `roster_players` rows where `checked_in=false AND weight='' AND photo_uri=''`; `protect_roster_rich_data_trigger` BEFORE UPDATE blocks downgrading `is_age_verified`, `photo_uri`, `weight`, `checked_in`; `public.clubs` carries `touch_clubs_updated_at` which writes `NEW.updated_at` even though `clubs` has no `updated_at` column, so bulk updates against `clubs` fail until the trigger is dropped or replaced. When diagnosing silent insert/update failures, query `pg_trigger`/`pg_get_triggerdef` against the live DB rather than trusting the migration history.
- `public.age_verified_registry` is the source of truth for who is age-verified; `roster_players.is_age_verified` can be cleared by buggy merges and must be backfilled from the registry (migration 028). The registry does not store `photo_uri`, so photos lost during a bad merge cannot be recovered without re-photographing.
- Three-tier authorization model: app-level admins via hardcoded email allowlist in `expo/lib/appAdmin.ts`; league admins via Supabase magic-link / email-OTP (Supabase-issued OTPs are NOT always 6 digits — they have appeared as 8 digits, and magic-link redirects must use the Expo deep link rather than localhost to reach the device); org-level editors via the `issue_editor_pin` Supabase RPC + `expo/lib/orgAdmin.ts`. Editor PINs are stored as `sha256(pin || org_id)` in `editor_pins.pin_hash`; custom PINs match `^[0-9]{4,10}$` and default to 480-minute expiry.
- Background workers: photo uploads must not block local saves — save the player record first, then enqueue via `expo/lib/photoUploadQueue.ts` (queue drains on launch, network reconnect, and post-save). Per-org reconcile uses the storage key `final_reconcile_v2_done:${orgId}` (`expo/lib/finalReconcile.ts`); the legacy global flag is honored once for backward compat.
- Seasons rotate by creating a brand-new org and flipping prior orgs to `organizations.is_active=false` (migration 040, partial-index `idx_organizations_is_active`); the prior org's roster is carried forward via per-season SQL migrations (041–045) keyed on deterministic IDs of the shape `s7s2026-{firstname}{lastname}-{yyyymmdd}` plus `ON CONFLICT (org_id, id) DO NOTHING`, so a re-run from device sync (which would otherwise re-create rows under their old `imported-*` IDs) cannot duplicate the row — partial carry-forward has produced inflated row counts (e.g. 1563 → 3728) and "all pending" new orgs when the device re-synced missing fields under the old IDs. `roster_players.age_group` is derived from `date_of_birth` using a July-1 rugby-year cutoff (migration 044: U6 if dob>2019-07-01, U8 >2017-07-01, U10 >2015-07-01, U12 >2013-07-01, U14 >2011-07-01); kids born ≤2011-07-01 age out and are bumped to U14 by migration 045. `roster_players.restriction_status` is independent of the free-text `division` column and uses the values `none | open_division | penny_player | play_up`.
